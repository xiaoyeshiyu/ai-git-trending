✨ firecrawl/pdf-inspector (6663★)

一句话：pdf-inspector 用 Rust 在本地快速判断 PDF 是扫描件还是原生文本，并把可提取的文本按版面结构转换成 Markdown。

  • 它是什么：这是 Firecrawl 开源的 PDF 检测与文本提取库，核心目标是先判断 PDF 类型，再决定是否需要 OCR。它可以识别 TextBased、Scanned、ImageBased、Mixed 等类型，并提取带坐标、字体信息和阅读顺序的文本，进一步转换为较干净的 Markdown。项目提供 Rust 原生库，同时有 Python、Node.js 和浏览器 WebAssembly 绑定。

  • 能解决什么痛点：很多 PDF 处理流水线会把所有文件都送进 OCR，成本高、延迟长，而大量报告、论文、发票、法律文档本身已经包含可提取文本。pdf-inspector 可以先在本地用几十毫秒判断哪些页面需要 OCR，避免对整份文档做不必要的 OCR。另一个痛点是 PDF 文本顺序和表格结构常常混乱，它内置多栏阅读顺序、标题、列表、表格和 Markdown 转换逻辑，适合直接进入后续检索或 RAG 流程。

  • 适合谁用：适合做文档解析、知识库导入、爬虫清洗、RAG 数据预处理的后端或数据工程师。也适合需要在 Node.js、Python 或浏览器端本地处理 PDF 的开发者，尤其是希望减少 OCR 服务调用的团队。

  • 怎么上手：Node.js 最简单可以直接安装使用：npm install @firecrawl/pdf-inspector，然后调用 processPdf(readFileSync('document.pdf')) 获取 pdfType 和 markdown。Python 侧 README 给出的方式是从源码用 maturin develop --release 安装后调用 pdf_inspector.process_pdf("document.pdf")。

  • 可以用在哪些场景：可以用于 PDF 上传入口的智能路由，先判断整份文档或具体页面是否需要 OCR，再分流到本地提取或 OCR 服务。可以用于把研究论文、财报、合同、发票等原生文本 PDF 转成 Markdown，供搜索索引、向量库或内部知识库消费。也可以在浏览器或 Web Worker 中运行 WebAssembly 版本，实现无需上传服务器的本地 PDF 预检和文本抽取。

  • 技术看点：项目用纯 Rust 实现，主要依赖 lopdf 解析 PDF，不依赖 ML 模型和外部服务；检测阶段通过解析 xref、页面树和内容流里的文本/图片操作符快速分类。提取阶段只加载一次文档，在检测、字体解析、ToUnicode CMap、布局分析、表格检测和 Markdown 转换之间复用解析结果，减少重复 I/O。

  • 近期动向与发展方向：最近 20 条提交集中在版本发布、WebAssembly 浏览器绑定、官网 demo、解析质量和基准测试更新上，说明项目正在从 Rust/Node/Python 扩展到浏览器本地运行场景。7 月中旬密集加入了表格候选评分、图表页拦截、标题序列识别、Markdown fidelity 输出、多栏和图像锚定区域排序等能力，开发重点明显偏向提高复杂版面转换质量。提交者以 Abimael Martell 为主，也有外部贡献者修复字体编码相关问题，社区参与还不算大，但维护节奏很活跃。

  • 同类对比：README 给出了与 liteparse、opendataloader、pymupdf4llm、markitdown 的本地解析基准对比。在 200 份 PDF 的 opendataloader-bench 语料上，pdf-inspector 的 Overall、Reading Order、Tables 和速度指标都排在前列，定位更偏向“无 OCR、快速、本地、结构化 Markdown 输出”，而不是通用 OCR 或模型型 PDF 解析器。

  • 注意事项：项目创建时间是 2026 年 2 月，仍然较新，当前有 54 个 open issues、贡献者 4 人，成熟度还需要结合实际文档集验证。它明确不做 OCR，因此扫描件、图片型 PDF 或字体编码严重损坏的文档仍需要回退到 OCR。近期多次发布 crates、npm、PyPI 和 wasm 版本，说明 API 与绑定仍在快速迭代，生产环境接入时应固定版本并准备回归样本文档。
